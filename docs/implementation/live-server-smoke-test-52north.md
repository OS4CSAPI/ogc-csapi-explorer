### Convention 3 Link Detection Analysis

This is the most significant finding from the 52North test, as this server relies entirely on Convention 3 for resource discovery.

#### How our `scanCsapiLinks` processes 52North's collection links:

Each collection has two `rel: "items"` links. Only the FIRST match wins (our loop uses `continue` after Convention 1/2, but Convention 3 doesn't — it just writes the map entry, so last-write-wins for duplicates with the same key).

| Collection      | HTML href             | Match?                       | JSON href                                | Match?                                       |
| --------------- | --------------------- | ---------------------------- | ---------------------------------------- | -------------------------------------------- |
| all_systems     | `/systems`            | ✅ `systems`                 | `/systems?f=application/json`            | ❌ segment = `systems?f=application/json`    |
| all_datastreams | `/datastreams`        | ✅ `datastreams`             | `/datastreams?f=application/json`        | ❌                                           |
| all_fois        | `/featuresOfInterest` | ❌ not in CSAPIResourceTypes | `/featuresOfInterest?f=application/json` | ❌                                           |
| all_procedures  | `procedures`          | ✅ `procedures`              | `procedures?f=application/json`          | ❌ segment = `procedures?f=application/json` |
| all_deployments | `deployments`         | ✅ `deployments`             | `deployments?f=application/json`         | ❌                                           |

**Convention 3 result for 52North collections:** `{ systems, datastreams, procedures, deployments }` — **4 of 5** detected.

#### Two bugs identified:

**Bug 1 (Moderate): Query parameters in href break Convention 3 parser**

Our `scanCsapiLinks` extracts the last path segment via:

```javascript
const segment = href.replace(/\/+$/, '').split('/').pop();
```

This does NOT strip query parameters. For `"/systems?f=application/json"`, the extracted segment is `"systems?f=application/json"`, which does not match `"systems"` in `knownTypes`.

**Impact:** If the HTML `rel: "items"` link appears first (as it does here), Convention 3 still works because the HTML href has no query params. But if a server only provides the JSON-format link, Convention 3 would fail.

**Fix:** Strip query parameters before extracting the segment:

```javascript
const segment = new URL(href, 'http://x').pathname
  .replace(/\/+$/, '')
  .split('/')
  .pop();
// OR simpler:
const segment = href.split('?')[0].replace(/\/+$/, '').split('/').pop();
```

**Bug 2 (Moderate): `featuresOfInterest` not recognized by Convention 3**

The OGC CSAPI standard uses `samplingFeatures` as the resource type name. However, 52North's collection links use `featuresOfInterest` as the href path. Our `CSAPIResourceTypes` array contains `samplingFeatures`, not `featuresOfInterest`.

This means Convention 3 cannot discover the features-of-interest endpoint on servers that use the `featuresOfInterest` path.

**Impact:** The server's `/samplingFeatures` endpoint DOES return 200, so URL generation works correctly if a user directly invokes the builder method. The issue is only with automatic discovery via `scanCsapiLinks` from collection links. Servers may route both `/samplingFeatures` and `/featuresOfInterest` to the same data — 52North routes `/samplingFeatures` to empty data but returns 404 for `/featuresOfInterest`.

**Fix options:**

1. Add `featuresOfInterest` as an alias in the Convention 3 matcher
2. Document it as a known server naming variation
3. Normalize in the matcher: `featuresOfInterest` → `samplingFeatures`

## New Findings

### F1 (Moderate): Convention 3 parser does not strip query parameters from href

**Severity:** Moderate
**Category:** Code bug
**Affects:** `scanCsapiLinks()` Convention 3 path — `helpers.ts` line ~152
**Evidence:** 52North collection links include `?f=application/json` in href, causing segment extraction to fail.
**Status:** Needs fix (minor — one-line change)

### F2 (Moderate): `featuresOfInterest` vs `samplingFeatures` naming discrepancy

**Severity:** Moderate
**Category:** Interoperability concern
**Affects:** Convention 3 discovery of features-of-interest resources
**Evidence:** 52North uses `featuresOfInterest` in collection hrefs; our `CSAPIResourceTypes` only contains `samplingFeatures`.
**Status:** Needs design decision — alias, normalize, or document

### F3 (Low): No CSAPI conformance classes advertised

**Severity:** Low
**Category:** Server limitation
**Affects:** `checkHasConnectedSystems()` conformance-based detection
**Evidence:** 52North only advertises `ogcapi-common-1/1.0/conf/core` — no CSAPI classes.
**Impact:** If we rely solely on conformance for CSAPI detection, this server would be missed. Our fallback (collection-level link scanning) works, but requires fetching the collections document.
**Status:** Informational — keep current multi-strategy detection approach

### F4 (Low): Mixed leading-slash convention in collection hrefs

**Severity:** Low
**Category:** Server inconsistency
**Affects:** Nothing in our code — we only inspect the last path segment
**Evidence:** `all_systems` → `/systems`, `all_procedures` → `procedures`
**Status:** Informational — no action needed

### F5 (Informational): Broken endpoints on 52North

**Severity:** Informational
**Category:** Server bugs (not our code)
**Evidence:** datastreams → 500, featuresOfInterest → 404, controlstreams → 404
**Status:** Server-side issues — does not affect our code

### F6 (Informational): Localhost leak in collections response

**Severity:** Informational
**Category:** Server configuration
**Evidence:** Outer links in `/collections` use `http://localhost:5000/...` URLs
**Status:** Server-side issue — does not affect our code

## Conclusion

Testing against a second implementation was highly valuable. While OpenSensorHub tests validated our URL generation and query parameter handling thoroughly, the 52North test exposed two real bugs in our Convention 3 link detection that would have been invisible in single-server testing:

1. Query parameters in `rel: "items"` hrefs break segment extraction
2. `featuresOfInterest` naming variant is not recognized

Both are fixable. The broader architectural differences (response envelope, conformance advertising, naming conventions) provide crucial data for Phase 3 response-parsing design.

**All Part 1 resource URLs our builder generates are accepted by this server** (200 for systems, deployments, procedures, samplingFeatures, properties). The interoperability issues are in discovery, not in URL construction.
