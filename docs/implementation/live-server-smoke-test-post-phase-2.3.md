## New Findings

### F1: Server rejects `systems/{id}/deployments` and `systems/{id}/procedures` (NEW)

**Severity:** Moderate (affects 2 of 28 methods)

The server returns 400 "Invalid resource name" for two system association endpoints:

```
GET /sensorhub/api/systems/03bc5ofvvstg/deployments
→ { "status": 400, "message": "Invalid resource name: 'deployments'" }

GET /sensorhub/api/systems/03bc5ofvvstg/procedures
→ { "status": 400, "message": "Invalid resource name: 'procedures'" }
```

**What works:** The server accepts all other nested paths under `/systems/{id}/`:

- `/subsystems` ✅
- `/history` ✅
- `/datastreams` ✅
- `/controlstreams` ✅
- `/samplingFeatures` ✅

**Analysis:** The OGC Connected Systems spec (23-001) defines that systems may link to their deployments and procedures via `/systems/{id}/deployments` and `/systems/{id}/procedures`. However, this server does not implement those sub-resource endpoints. The top-level `/deployments` and `/procedures` endpoints work fine — it's only the system-scoped navigation that's rejected.

This is a server implementation gap, not a bug in our code. Our `getSystemDeployments()` and `getSystemProcedures()` methods generate spec-correct URLs. A different server implementation (or a future version of this server) may support them.

**Impact on our code:** None. The URL patterns are correct per spec. When we build the fetch layer in Phase 3, we should handle 400 responses gracefully for optional sub-resource endpoints.

---

### F2: Procedures and Deployments have no data on this server

**Severity:** Informational (testing limitation)

The server has zero procedures and zero deployments registered. This means:

- `getProcedures()`, `getDeployments()` return `{ items: [] }` — URL confirmed correct
- Individual resource GET/PUT/DELETE and all nested endpoints cannot be end-to-end validated
- Only list + query parameter endpoints can be confirmed

**Impact:** We've confirmed that the top-level URL patterns (`/procedures`, `/procedures?limit=N`, `/procedures?q=...`) are accepted by the server. The nested resource patterns (`/procedures/{id}/systems`, `/procedures/{id}/datastreams`, `/procedures/{id}/history`) follow the exact same URL construction path (`buildResourceUrl`) that works for systems, so they are extremely likely to be correct. But we cannot prove it until the server has procedure data.

---

### F3: Properties endpoint returns empty, no `properties` link in root document (INFORMATIONAL)

**Severity:** Informational

The server advertises `property` conformance (`ogcapi-connectedsystems-1/1.0/conf/property`) and the `/properties` endpoint returns 200 with empty items. However, the root API document does **not** include a `rel: "properties"` link — it only lists systems, deployments, procedures, samplingFeatures, datastreams, and observations.

This means `scanCsapiLinks` on the root document would not detect `properties` as an available resource type. It would only be detected if a collection has a link pointing to it (Convention 3), or if we add an explicit `properties` link convention.

**Impact on our code:** When we implement Issue #9 (Properties methods), we'll need to verify that resource discovery works for this type. Currently, our code would not detect properties from this server's root document. This may require either:

1. The collection document has a `rel: "items"` link with `href` containing `properties` (not checked yet)
2. Or we add a conformance-based discovery fallback (Phase 3 concern)

## Data Shape Observations (Phase 3 Reference)

Observations from this session relevant to future parsing work:

1. **SamplingFeatures** ARE GeoJSON Features — `type: "Feature"`, `id`, `geometry` (null for these), `properties` with `uid`, `featureType`, `name`. Uses `featureType: "http://www.opengis.net/sensorml/2.0#Feature"` — note this is a SensorML URI, not SOSA.

2. **ControlStreams** have a flat structure similar to Datastreams — `id`, `name`, `description`, `system@id`, `system@link`, `inputName`, `validTime` (array format), `issueTime` (array format), `controlledProperties`, `formats`.

3. **System individual resources** include a `links` array with `rel: "datastreams"` pointing to the nested endpoint — this provides an alternative discovery mechanism for sub-resources beyond the URL-pattern-based approach our builder uses.

4. **Format parameter (`f`)** works on individual resources — `?f=sml3` returns `application/sml+json` content type. Our builder's `f` parameter support is confirmed functional.

## Verdict

**All Phase 2.1/2.2 fixes remain working. No regressions.** The critical F1/F2 fixes continue to function correctly against the live server.

**Procedures endpoints are confirmed functional.** The top-level `/procedures` endpoint accepts all query parameter patterns our builder generates (`limit`, `offset`, `q`). The server has no procedure data, so nested endpoints could not be end-to-end validated — but the URL construction path is identical to the systems path, which is proven to work.

**One new moderate finding:** The server rejects `/systems/{id}/deployments` and `/systems/{id}/procedures` with 400 "Invalid resource name". This is a server limitation, not a bug in our code — our URLs are spec-compliant. These sub-resource endpoints may work on other implementations or future versions of this server.

**Query parameter coverage expanded significantly.** This smoke test validated `bbox`, `datetime`, `id`, `recursive`, and `f` parameters that were not tested in previous smoke tests. All are accepted by the server.

**The codebase is ready to proceed with Phase 2.4 (Issues #8–#9: SamplingFeatures, Properties).**
