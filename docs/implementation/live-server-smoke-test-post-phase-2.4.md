No code changes were made. All tests were run from the terminal using raw HTTP calls (`Invoke-RestMethod` / `Invoke-WebRequest`) that simulate the URL patterns generated by `CSAPIQueryBuilder`. The goal was to verify that all 36 public methods produce URLs both servers accept, with a focus on:

## New Findings

### F8: OSH rejects `samplingFeatures/{id}/systems` (NEW)

**Severity:** Moderate — affects 1 of 36 methods  
**Classification:** Server limitation, not a client bug

```
GET /sensorhub/api/samplingFeatures/040g/systems → 400
```

OSH does not implement the nested `/samplingFeatures/{id}/systems` route. This is the same pattern as the known F6/F7 findings where certain nested association endpoints are not supported. Our URL is correctly formed per the CSAPI spec.

**Action:** None required. Document as server limitation.

### F9: OSH rejects `samplingFeatures/{id}/history` (NEW)

**Severity:** Moderate — affects 1 of 36 methods

OSH does not implement history for SamplingFeatures. Our URL is correctly formed per the CSAPI spec.

### F11: 52North uses SensorML format for individual resources (OBSERVATION)

**Severity:** Moderate — interoperability concern for Phase 3 response parsing

OSH returns individual resources as **GeoJSON Features**:

```json
{
  "type": "Feature",
  "id": "03bc5ofvvstg",
  "geometry": null,
  "properties": { "uid": "...", "featureType": "...", "name": "..." }
}
```

52North returns individual resources as **SensorML objects**:

```json
{
  "type": "PhysicalSystem",
  "definition": "sosa:Sensor",
  "id": "5400-526",
  "label": "Doppler Current Profiler Sensor",
  "uniqueId": "urn:sensor:5400-526"
}
```

Both are valid per the CSAPI spec (which supports both GeoJSON and SensorML representations), but Phase 3 response parsing will need to handle both formats.

**Action:** Phase 3 design must account for dual response formats.

### F12: 52North `systems/{id}/deployments` works (POSITIVE)

**Severity:** Informational — positive finding

52North returns 200 for `systems/5400-526/deployments` (1 item), while OSH returns 400 for the same nested route pattern. This confirms the URL pattern is correct and that server support varies.

**Action:** None required. Confirms our URL generation is correct.

### F13: Both servers now use `items` envelope (CONFIRMATION)

**Severity:** Informational — confirms prior F3

Both OSH and 52North now return collections in `{ items: [...], links: [...] }` format. 52North previously used `{ type: "FeatureCollection", features: [...] }` in our initial test. The `items` envelope is now consistent across both servers.

**Action:** Phase 3 response parsing should target `items` as the standard collection envelope.

### Phase 3 Implications

Based on this smoke test, Phase 3 response parsing must handle:

- **Dual collection envelopes:** Both servers use `items`, but future servers may use `features`
- **Dual individual formats:** GeoJSON Feature (OSH) vs. SensorML (52North)
- **Graceful degradation:** Many nested endpoints return 400 or 500 — response parsing should handle errors cleanly
- **Link-based pagination:** Both servers use `next`/`prev` link relations (no numeric pagination metadata)
