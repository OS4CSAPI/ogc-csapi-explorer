## New Findings

### F14 (Moderate): Properties not discoverable via any link detection convention

**Severity:** Moderate — affects Properties discovery path  
**Category:** Interoperability concern  
**Affects:** `scanCsapiLinks()` in `helpers.ts`, `assertResourceAvailable()` in `url_builder.ts`  
**Ownership:** Shared (server configuration + client discovery)

**Evidence:**

| Discovery Method                | OSH                               | 52North                        |
| ------------------------------- | --------------------------------- | ------------------------------ |
| Convention 1 (ogc-cs: prefix)   | ❌ No `ogc-cs:properties` link    | ❌ No `ogc-cs:properties` link |
| Convention 2 (plain rel)        | ❌ No `rel: "properties"` in root | ❌ No CSAPI links in root      |
| Convention 3 (collection items) | ❌ No properties collection       | ❌ No properties collection    |
| Direct URL                      | ✅ `/properties` returns 200      | ✅ `/properties` returns 200   |

Both servers implement the `/properties` endpoint (returns 200 with empty `items`), but neither server advertises properties through any of the three link detection conventions our `scanCsapiLinks()` function supports. This means:

1. `CSAPIQueryBuilder` cannot discover properties via its current link scanning
2. `assertResourceAvailable('properties')` will throw `EndpointError` even though the endpoint exists
3. Users would need to bypass the builder and construct the URL manually

OSH root document has links for 6 resource types (`systems`, `deployments`, `procedures`, `samplingFeatures`, `datastreams`, `observations`) — notably missing `properties` and `controlstreams`. OSH collections include 4 of these 6. Neither path includes properties.

52North has no CSAPI-specific root links and 5 collections — also excluding properties.

**Impact:** Low for Phase 2 (URL building is tested and correct). Moderate for Phase 3 (auto-discovery won't detect properties). Our `assertResourceAvailable` guard is working correctly — it correctly reports that the link isn't advertised. The underlying endpoint works; the discovery metadata is missing.

**Status:** Informational — not a code bug. Both servers simply don't advertise properties in their link structures. When a server does advertise properties (via any convention), our code will handle it correctly. This is Phase 3 design input for fallback/probing strategies.

## Verdict

**No regressions. No code bugs. All 42 methods generate correct URLs.**

The Properties implementation (Issue #9) is validated against both servers. Both servers accept the `/properties` endpoint and all tested query parameters, returning 200 with empty results (no property data populated on either server). The 5 nested Properties methods (`getProperty`, `getPropertySystems`, `getPropertyDataStreams`, `getPropertyControlStreams`, `getPropertyHistory`) could not be tested with real data but their URL patterns are correct — they follow the identical `buildResourceUrl` path proven by all other resource types.

The one new finding (F14) is a discovery concern, not a code bug: neither server advertises properties through any of the three link detection conventions our `scanCsapiLinks()` supports. The `/properties` endpoint exists and works on both servers, but `assertResourceAvailable('properties')` would correctly throw because the link metadata is absent. This is Phase 3 design input — a fallback/probing strategy may be needed for resource types that servers implement but don't advertise.

The Phase 2.5 codebase (42 methods, 209 tests, Issue #40 debt cleanup, Issue #41 review findings fix) is confirmed clean and ready for Phase 2 Part 2 resources (Issues #10–#13: DataStreams, Observations, ControlStreams, Commands).
