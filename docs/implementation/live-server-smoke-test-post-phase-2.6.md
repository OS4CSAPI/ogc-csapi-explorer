## Test Methodology

No code changes were made. All tests were run from the terminal using raw HTTP calls (`Invoke-RestMethod` / `Invoke-WebRequest`) that simulate the URL patterns generated by `CSAPIQueryBuilder`. The goal was to verify that all 53 public methods produce URLs both servers accept, with a focus on:

1. The 11 new DataStreams methods from Phase 2.6 (Issue #10)
2. DataStreams query parameter acceptance (systemId, phenomenonTime, resultTime, cursor, f, q, offset)
3. Observation and schema response shapes (Phase 3 reference)
4. `resultTime=latest` special value acceptance
5. Regression check on all prior findings (F1–F15)

### F19 (Informational): `resultTime=latest` accepted by OSH

**Severity:** Informational — confirms type gap is real  
**Category:** Interoperability concern  
**Affects:** `DateTimeParameter` type in `model.ts`, `formatDateTimeParameter` in `helpers.ts`  
**Ownership:** Ours (type system limitation)

**Evidence:**

```
GET .../datastreams/03tbj7mvqg50/observations?resultTime=latest&limit=1 → 200 (0 items)
```

OSH accepts `resultTime=latest` as a valid parameter value. This confirms that the `resultTime: 'latest'` capability documented in the implementation guide (commit `8bfa724`, §6 temporal parameters) is a real server feature. Our `DateTimeParameter` type cannot currently represent the string `'latest'` — only `Date` objects and date ranges. The fix plan (extend type, update formatter, add test) is already documented and scheduled for pre-Phase 3.

**Status:** Informational. Already documented and tracked.

## Data Shape Observations (Phase 3 Reference)

1. **Datastream list envelope:** `{ items: [...], links: [...] }` — matches the `items` pattern from F3/F13. Pagination via `rel: "next"` link with offset parameter.

2. **Single datastream shape:** Contains `id`, `name`, `system@id`, `system@link`, `outputName`, `validTime` (array!), `observedProperties` (array), `resultType`, `formats` (array of mime types), `links` (array). The `system@id` field uses `@` notation for cross-references.

3. **Observation shape:** `{ id, datastream@id, phenomenonTime, resultTime, result: {...} }` — flat object within `items` array. `result` is an arbitrary JSON object whose structure depends on the datastream schema.

4. **Schema shape:** `{ obsFormat, recordSchema: { type: "DataRecord", fields: [...] } }` — SWE Common DataRecord with typed fields (Time, Quantity, etc.). Each field has `type`, `name`, `definition`, `label`, `description`, `uom`.

5. **Datastream `validTime` uses array format:** `["2026-01-26T18:32:01.56Z", "now"]` — same array pattern as F4, including the special `"now"` string. Phase 3 must handle this.

6. **Datastream `formats` lists 5 observation formats:** `om+json`, `swe+json`, `swe+csv`, `swe+xml`, `swe+binary`. The `obsFormat` parameter on the schema endpoint should be one of these.

7. **Cross-reference notation:** Datastreams use `system@id` and `system@link` to reference the parent system. Observations use `datastream@id`. This `@` notation is consistent across resource types.

## Verdict

**No regressions. No code bugs. All 53 methods generate correct URLs.**

The DataStreams implementation (Issue #10) is validated against OSH. 8 of 11 methods produce successful 200 responses with real data. The 3 failures (F16/F17/F18 — `datastreams/{id}/systems`, `datastreams/{id}/procedures`, `datastreams/{id}/history`) are all server-side 400 rejections following the same pattern as F6–F9. These are spec-correct URLs that OSH does not implement. Our code is correct; the server has partial Part 2 support for association and history sub-endpoints.

The big positive surprise is **F19: `resultTime=latest` is accepted by OSH** (200 response). This confirms that the type gap documented in the implementation guide is a real capability we need to support. The 3-step fix plan (extend `DateTimeParameter`, update formatter, add test) should be completed before Phase 3.

52North's DataStreams endpoint remains broken (500 on all requests), meaning DataStreams can only be cross-validated against a single server. This is a testing limitation, not a code concern — our URLs are spec-correct.

**Data shape observations for Phase 3:** Observation responses use the `items` envelope with flat objects containing `phenomenonTime`, `resultTime`, and a `result` object whose shape is schema-dependent. Datastreams use `@` notation for cross-references (`system@id`, `datastream@id`). The schema endpoint returns SWE Common DataRecords. These observations are captured above for Phase 3 design reference.

The Phase 2.6 codebase (53 methods, 242 tests, 6 resource types) is confirmed clean and ready for the next Part 2 resource type (Issue #11 — Observations Methods).
