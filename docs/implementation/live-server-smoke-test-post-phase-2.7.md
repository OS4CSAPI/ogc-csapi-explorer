## Test Methodology

No code changes were made during testing. All tests were run from the terminal using raw HTTP calls (`Invoke-RestMethod` / `Invoke-WebRequest`) that simulate the URL patterns generated by `CSAPIQueryBuilder`. The goal was to verify that all 61 public methods produce URLs both servers accept, with a focus on:

1. The 8 new standalone Observations methods from Phase 2.7 (Issue #11)

3. Observations query parameter acceptance (resultTime=latest, phenomenonTime, q, offset, f, id)
4. Observations singular association paths (`/datastream`, `/samplingFeature`, `/system`)
5. Observation data shape observations (Phase 3 reference)
6. Regression check on all prior findings (F1–F20)

## New Findings

### F21 (Moderate): OSH rejects `observations/{id}/datastream` (singular)

**Severity:** Moderate — server limitation for singular association endpoint  
**Category:** Server limitation  
**Affects:** `getObservationDatastream()` in `url_builder.ts`  
**Ownership:** Upstream (server-side)

**Evidence:**

```
GET .../observations/0829d6supc31trqfo0/datastream → 400
```

Our URL uses the **singular** sub-path `/datastream` because each observation belongs to exactly one datastream. The Part 2 spec supports this pattern, but OSH returns 400. This is consistent with the OSH pattern of rejecting association sub-endpoints (F6–F9, F16–F18). The observation itself contains `datastream@id: "083g"`, proving the relationship exists — it's just not exposed as a sub-endpoint.

**Status:** Server limitation. URL generation is correct. No code fix needed.

### F27 (Informational): Observation `foi@id` uses abbreviated notation

**Severity:** Informational — Phase 3 reference  
**Category:** Naming variation  
**Affects:** Observation response parser (Phase 3)  
**Ownership:** Client (Phase 3)

**Evidence:**

```json
{
  "id": "0829d6supc31trqfo0",
  "datastream@id": "083g",
  "foi@id": "080g",
  "phenomenonTime": "2026-01-14T12:35:34.519Z",
  "resultTime": "2026-01-14T12:35:34.519Z",
  "result": { "location": { "lat": 24.18, "lon": 120.65, "alt": 127.9 } }

```

Where DataStreams use `system@id` for the parent system cross-reference, Observations use `foi@id` for the sampling feature cross-reference — NOT `samplingFeature@id`. The abbreviation `foi` stands for "Feature of Interest" and is consistent with 52North's `featuresOfInterest` naming. Phase 3 must handle this notation.

**Status:** Informational. Phase 3 concern.

## Data Shape Observations (Phase 3 Reference)

1. **Standalone observation list envelope:** `{ items: [...], links: [...] }` — same `items` pattern as all other resource types (F3/F13). Pagination via `rel: "next"` link with offset parameter.

2. **Single observation shape (confirmed from standalone endpoint):**

   ```json
   {
     "id": "0829d6supc31trqfo0",
     "datastream@id": "083g",
     "foi@id": "080g",
     "phenomenonTime": "2026-01-14T12:35:34.519Z",
     "resultTime": "2026-01-14T12:35:34.519Z",
     "result": { "location": { "lat": 24.18, "lon": 120.65, "alt": 127.9 } }
   }
   ```

   Key fields: `id`, `datastream@id`, `foi@id`, `phenomenonTime`, `resultTime`, `result`.

3. **`foi@id` cross-reference notation:** Uses `foi@id` (Feature of Interest), not `samplingFeature@id`. This is a naming variation from the `system@id` / `datastream@id` pattern. Phase 3 must map `foi@id` ↔ `samplingFeature` in the response parser.

4. **`result` field is schema-dependent:** One observation has `{ location: { lat, lon, alt } }`, another has `{ StatusType: "INFO", Status: "..." }`. The structure depends on the parent datastream's schema (retrievable via `getDataStreamSchema()`).

5. **`resultTime=latest` returns real data on standalone endpoint:** 2 observations returned — one per active datastream that has recent data. This is a practical "get the latest from all sensors" query pattern.

6. **Pagination uses offset (not cursor):** The `next` link on observations uses `offset=2`, not a cursor token. This is different from what the Phase 2.7 code review F8 noted about cursor pagination — the server uses offset-based pagination for observations despite the spec supporting cursor.

## Verdict

**No regressions. No code bugs. All 61 methods generate correct URLs.**

The Observations implementation (Issue #11) is validated against OSH. 4 of 8 methods produce successful 200 responses with real data. The 4 failures (F21–F24 — `observations/{id}/datastream`, `observations/{id}/samplingFeature`, `observations/{id}/system`, `observations/{id}/history`) are all server-side 400 rejections following the identical pattern established by F6–F9 (Part 1) and F16–F18 (DataStreams). **OSH consistently rejects association and history sub-endpoints across all resource types.** Only `systems/{id}/history` is an exception — it works. Our URLs are spec-correct; the pattern is purely a server-side limitation.

The highlight of this smoke test is **F25: `resultTime=latest` returns real data** on the standalone observations endpoint. In Phase 2.6, this value was accepted (200) but returned 0 items via the per-datastream path. Now, via the standalone `/observations?resultTime=latest` path, it returns 2 observations — one per active datastream with the most recent result time. This validates the complete Issue #43 fix pipeline: `CsapiDateTimeParameter` type alias → `formatDateTimeParameter` guard clause → URL generation → server acceptance → real data returned.

**Observations data shapes for Phase 3** reveal two important parser considerations: (1) the `foi@id` notation for sampling feature cross-references (not `samplingFeature@id`), and (2) the `result` field structure being entirely schema-dependent. Phase 3 must handle both of these.

The Phase 2.7 codebase (61 methods, 267 tests, 7 resource types) is confirmed clean and ready for the next Part 2 resource types (Issue #12 — ControlStreams Methods, Issue #13 — Commands Methods).
