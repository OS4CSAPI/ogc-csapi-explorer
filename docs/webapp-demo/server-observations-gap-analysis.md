# Server Observations Gap Analysis — OSH SensorHub & 52North CSA

> **Date**: 2026-02-16
> **Context**: During integration testing and CRUD smoke testing against two live OGC Connected Systems API servers — OSH SensorHub (`http://45.55.99.236:8080/sensorhub/api`) and 52North CSA (`https://csa.demo.52north.org`) — nine server-side observations were identified. These document real server behaviors that affect library consumers but are **not bugs in the client library itself**. They inform documentation, defensive coding practices, and workaround strategies.

## Detailed Breakdown of Each Observation

---

### S-1. OSH SensorHub: No REST Datastream Creation

| | |
|---|---|
| **Severity** | Medium |
| **Server** | OSH SensorHub |
| **Endpoint** | `POST /systems/{id}/datastreams` |
| **Discovered In** | E2E write operations test |

#### What happens

OSH rejects `POST /systems/{id}/datastreams` for **all** Content-Types tested (7 types including `application/json`, `application/geo+json`, `application/swe+json`, `application/sml+json`). Response: `400 "Unsupported format"`.

#### Why

Datastreams in OSH are auto-generated by internal sensor drivers (Java SPI plugins), not created via REST API. The OSH architecture ties datastreams to live sensor instances that produce data — you can't create a "detached" datastream via REST.

#### Evidence

From E2E write operations test:
```
POST /systems/03bc5ofvvstg/datastreams
Content-Type: application/json
→ 400 "Unsupported format: application/json"

POST /systems/03bc5ofvvstg/datastreams
Content-Type: application/sml+json
→ 400 "Unsupported format: application/sml+json"
```

Seven different Content-Type values all produced the same rejection.

#### Update (2026-02-16): Partially Resolved

During CRUD smoke testing, we discovered that **REST datastream creation does work** on OSH — but only for systems created via REST (not pre-existing sensor-driven systems). The original S-1 finding was tested against sensor-driven systems whose datastreams are managed by internal drivers. For REST-created systems, `POST /systems/{id}/datastreams` succeeds with `Content-Type: application/json` and `obsFormat: "application/swe+json"` (see also S-9).

#### Impact on consumers

Any admin UI or client that expects full CRUD on datastreams will fail on sensor-driven systems but succeed on REST-created systems. The library should document that datastream creation behavior is system-dependent on OSH.

### S-2. OSH SensorHub: Live Datastreams Are Read-Only

| | |
|---|---|
| **Severity** | Medium |
| **Server** | OSH SensorHub |
| **Endpoint** | `POST /datastreams/{id}/observations` |
| **Discovered In** | E2E write operations test |

#### What happens

`POST /datastreams/{id}/observations` returns `400 "Resource is not writable"` for existing sensor-driven datastreams. The datastreams are actively receiving data from physical sensors and are marked read-only at the server level.

#### Why

Sensor-driven datastreams have their observation flow managed by the sensor driver. The REST API cannot inject observations into a live sensor stream — this would break the data integrity model where each observation is tied to a specific sensor reading.

#### Evidence

```
POST /datastreams/03tbj7mvqg50/observations
Content-Type: application/om+json
→ 400 "Resource is not writable"
```

#### Impact on consumers

Observation creation only works on datastreams explicitly created for that purpose via REST (on REST-created systems). Combined with S-1's original finding, this creates a chicken-and-egg problem for testing write operations against sensor-driven OSH resources. The CRUD smoke test works around this by creating its own systems and datastreams from scratch.

### S-3. 52North: Declares Zero CSA Conformance Classes

| | |
|---|---|
| **Severity** | High |
| **Server** | 52North CSA |
| **Endpoint** | `GET /conformance` |
| **Discovered In** | Cross-server interoperability test |

#### What happens

52North's `/conformance` endpoint only declares `ogcapi-common-1/1.0/conf/core`. It does not declare any Connected Systems API conformance classes despite implementing Part 1 resources (3 systems, 1 deployment, 1 procedure).

#### Evidence

```json
GET /conformance
{
  "conformsTo": [
    "http://www.opengis.net/spec/ogcapi-common-1/1.0/conf/core"
  ]
}
```

No CSA conformance URIs (e.g., `http://www.opengis.net/spec/ogcapi-connectedsystems-1/1.0/conf/...`) are declared.

#### Why it matters

This is the highest-severity server observation because it directly affects library behavior. Any library logic that gates CSAPI features on conformance class declarations will incorrectly conclude that 52North doesn't support CSA. This was the key architectural finding that led the demo app to bypass `OgcApiEndpoint` entirely (see [conformance bypass architecture notes](./conformance-bypass-architecture-notes.md)).

#### Impact on consumers

- Library consumers using `OgcApiEndpoint` won't discover any CSA resources on 52North
- The library should **not** rely solely on conformance declarations to determine CSAPI availability
- Resource-sniffing (trying known CSA endpoints and checking for valid responses) is more reliable than conformance checking

#### Related

- [Conformance bypass architecture notes](./conformance-bypass-architecture-notes.md) — Detailed analysis of why the demo app bypasses `OgcApiEndpoint`

### S-4. 52North: Part 2 Endpoints Return 400/500

| | |
|---|---|
| **Severity** | Medium |
| **Server** | 52North CSA |
| **Endpoint** | `GET /datastreams`, `GET /observations`, etc. |
| **Discovered In** | Cross-server interoperability test |

#### What happens

DataStreams and Observations endpoints are not implemented on 52North. Requests return errors:

| Request | Response |
|---|---|
| `GET /datastreams` with `Accept: application/json` | HTTP 500 Internal Server Error |
| `GET /datastreams` with `Accept: application/sml+json` | HTTP 400: `"expected [] got 'application/sml+json'"` |

#### Why

52North only implements Part 1 of the Connected Systems API (systems, deployments, procedures, sampling features). Part 2 resources (datastreams, observations, control streams, commands) are not available.

#### Impact on consumers

52North is Part 1 only. Library consumers should handle 400/500 responses from Part 2 endpoints gracefully rather than assuming all CSAPI servers implement the full spec. A robust library should:
1. Probe Part 2 availability independently of Part 1
2. Not crash on 400/500 from Part 2 endpoints
3. Report Part 2 as unavailable rather than treating server errors as client failures

### S-5. OSH SensorHub: Omits Standard `rel="data"` Link

| | |
|---|---|
| **Severity** | Low |
| **Server** | OSH SensorHub |
| **Endpoint** | `GET /` (API root) |
| **Discovered In** | Library integration testing |

#### What happens

OSH uses resource-name-based link relations directly on the root document (e.g., links with `rel="systems"`, `rel="datastreams"`, `rel="deployments"`) rather than the standard `rel="data"` pointing to `/collections` as an intermediate step.

#### Evidence

```json
GET /
{
  "links": [
    { "rel": "systems", "href": ".../systems", "type": "application/json" },
    { "rel": "deployments", "href": ".../deployments", "type": "application/json" },
    { "rel": "datastreams", "href": ".../datastreams", "type": "application/json" }
  ]
}
```

No `rel="data"` link to `/collections` is present.

#### Impact on consumers

The library's `scanCsapiLinks()` function handles this correctly — it recognizes both the standard `rel="data"` → `/collections` pattern and the direct resource-name-based relations. This observation is documented for completeness; no workaround is needed in practice.

However, it means the OGC CSA spec allows legitimate variation in how servers expose their resource collections, and libraries must support both patterns.

### S-6. 52North: SSL Certificate Expired

| | |
|---|---|
| **Severity** | Low |
| **Server** | 52North CSA |
| **Endpoint** | All (HTTPS connection level) |
| **Discovered In** | Initial connection test |

#### What happens

The 52North demo server at `https://csa.demo.52north.org` has an expired SSL certificate. All HTTPS connections fail unless certificate validation is disabled:
- **Node.js**: `NODE_TLS_REJECT_UNAUTHORIZED=0`
- **Vite proxy**: `secure: false`
- **Browsers**: refuse direct connection entirely

#### Impact on consumers

This is a server operations issue, not a library concern. The demo app routes all 52North traffic through a Vite proxy with `secure: false` to work around it. A production deployment would need either:
1. The server operator to renew the certificate
2. A backend proxy that bypasses certificate validation
3. Browser-side certificate exception (not programmatically controllable)

### S-7. 52North: Write Preflight CORS Fails

| | |
|---|---|
| **Severity** | Medium |
| **Server** | 52North CSA |
| **Endpoint** | All (OPTIONS preflight) |
| **Discovered In** | [CORS preflight test](./cors-preflight-test-results.md) |

#### What happens

52North's server is missing `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` in OPTIONS preflight responses. Browsers block all POST/PUT/DELETE requests due to CORS policy violations.

#### Evidence

```
OPTIONS /systems
→ 200 OK
   Access-Control-Allow-Origin: *
   (missing Access-Control-Allow-Methods)
   (missing Access-Control-Allow-Headers)
```

Without `Access-Control-Allow-Methods: POST, PUT, DELETE` and `Access-Control-Allow-Headers: Content-Type, Authorization`, browsers reject the preflight and never send the actual request.

#### Impact on consumers

Any browser-based client must proxy write requests to 52North. The demo app handles this through its Vite proxy. In practice, 52North appears to be read-only anyway (returns `401 Unauthorized` on write attempts), so CORS for writes is academic — but it prevents even testing error handling for write operations.

#### Related

- [CORS preflight test results](./cors-preflight-test-results.md) — Detailed CORS test methodology and results

### S-8. OSH SensorHub: Rejects `Accept: application/geo+json` on POST

| | |
|---|---|
| **Severity** | Medium |
| **Server** | OSH SensorHub |
| **Endpoint** | `POST /systems`, `POST /deployments`, etc. |
| **Discovered In** | CRUD smoke test |

#### What happens

POST requests with `Accept: application/geo+json` header cause network-level failures on OSH SensorHub. The same request with `Accept: application/json` (or no explicit Accept header) succeeds with `201 Created`.

#### Evidence

From CRUD smoke test (commit `f3dd4ee`):
- **With** `Accept: application/geo+json` → Network error / rejection
- **Without** explicit Accept header → `201 Created` (empty body, `Location` header returned)

#### Why it likely happens

OSH returns empty bodies on 201 responses. The `Accept` header is irrelevant when there's no response body, but OSH appears to validate it against its supported response formats **before** processing the request. Since the POST response format isn't `application/geo+json` (it's an empty body), the server rejects the mismatched Accept header.

#### Impact on consumers

Library issue [#9 — Default to Accept: application/geo+json for Part 1 resource requests](https://github.com/OS4CSAPI/ogc-csapi-explorer/issues/9) should note that this default should apply to **GET requests only**, not POST/PUT/DELETE operations where the response is typically empty or status-only.

#### Workaround applied in demo app

The smoke test sends `Content-Type` headers on POST/PUT but omits `Accept` headers on write operations:

```typescript
// Only send Content-Type, NOT Accept — OSH may reject Accept: application/geo+json
headers: { 'Content-Type': contentType }
```

#### Related

- [#9 — Default to Accept: application/geo+json for Part 1 resource requests](https://github.com/OS4CSAPI/ogc-csapi-explorer/issues/9) — Should scope recommendation to GET only
- [CRUD smoke test findings](./crud-smoke-test-findings.md) — First documented in S-8 section

### S-9. OSH SensorHub: Rejects `obsFormat: "application/json"` in Datastream Schema Payloads

| | |
|---|---|
| **Severity** | Medium |
| **Server** | OSH SensorHub |
| **Endpoint** | `POST /systems/{id}/datastreams` |
| **Discovered In** | CRUD smoke test |

#### What happens

When creating a datastream, the `schema.obsFormat` field in the request body specifies what format observations will use. OSH rejects `"application/json"` as an `obsFormat` value:

```json
{
  "status": 400,
  "message": "Unsupported format: application/json"
}
```

The error refers to the **payload body field**, not the HTTP `Content-Type` header. The HTTP `Content-Type: application/json` is accepted — it's the `obsFormat` value inside the schema that's rejected.

#### Evidence

Systematic testing of different `obsFormat` values against `POST /systems/0470/datastreams`:

| `obsFormat` Value | HTTP Response | Result |
|---|---|---|
| `application/json` | `400 Bad Request` | `"Unsupported format: application/json"` |
| `application/sml+json` | `400 Bad Request` | `"Unsupported format: application/sml+json"` |
| `application/om+json` | `500 Internal Server Error` | Server crash (accepted format, parsing error) |
| **`application/swe+json`** | **`201 Created`** | **Success** |

Only `application/swe+json` is accepted as an `obsFormat` value.

#### Why it's a conformance gap

The OGC Connected Systems API Part 2 OpenAPI specification's own example file ([datastream-simple-create.json](https://opengeospatial.github.io/ogcapi-connected-systems/api/part2/openapi/examples/datastreams/datastream-simple-create.json)) explicitly uses `obsFormat: "application/json"`:

```json
{
  "name": "Indoor Thermometer 001 - Living Room Temperature",
  "schema": {
    "obsFormat": "application/json",
    "resultSchema": {
      "name": "temp",
      "type": "Quantity",
      ...
    }
  }
}
```

OSH rejecting this spec-compliant value means clients must know **per-server** which `obsFormat` values are supported. The spec doesn't provide a discovery mechanism for supported observation formats at the datastream creation level.

#### Additional note: `application/om+json` causes 500

The `application/om+json` format was accepted (no "Unsupported format" error) but caused an internal server error, suggesting OSH has partial/broken support for the O&M JSON format. This is a separate server bug.

#### Impact on consumers

- Clients following the OGC spec example will fail on OSH
- The supported `obsFormat` values are not discoverable — they're only listed on **existing** datastreams' `formats` array (e.g., `["application/om+json", "application/swe+json", "application/swe+csv", ...]`)
- Library documentation should note that `application/swe+json` is the safest `obsFormat` for OSH compatibility

#### Workaround applied in demo app

Changed the smoke test's datastream and controlStream payloads to use `application/swe+json`:

```typescript
// Before (spec-compliant but OSH-rejected):
schema: { obsFormat: 'application/json', recordSchema: { ... } }

// After (OSH-compatible):
schema: { obsFormat: 'application/swe+json', recordSchema: { ... } }
```

Committed at [`7f7510f`](https://github.com/OS4CSAPI/ogc-csapi-explorer/commit/7f7510f).

#### Related

- S-1 (updated) — REST datastream creation does work on REST-created systems, but requires the correct `obsFormat`
- [#6 — Add CSAPI_CONTENT_TYPES helper map](https://github.com/OS4CSAPI/ogc-csapi-explorer/issues/6) — Should include guidance on `obsFormat` values alongside HTTP Content-Type values

## Impact Assessment

### By Server

**OSH SensorHub** (5 observations: S-1, S-2, S-5, S-8, S-9):
- Most observations relate to the distinction between sensor-driven resources (auto-managed, read-only) and REST-created resources (full CRUD)
- S-8 and S-9 are conformance gaps where the server rejects spec-compliant requests
- S-5 is a minor link structure difference that the library already handles

**52North CSA** (4 observations: S-3, S-4, S-6, S-7):
- S-3 (zero conformance) is the most impactful — it breaks conformance-based feature discovery
- S-4 (Part 2 not implemented) is expected and easy to handle
- S-6 and S-7 are infrastructure/operations issues, not API behavior issues

### By Impact on Library Design

| Impact Area | Observations | Recommendation |
|---|---|---|
| **Feature discovery** | S-3, S-5 | Don't gate on conformance alone; support multiple link patterns |
| **Write operations** | S-1, S-2, S-8 | Omit Accept on writes; document system-dependent behavior |
| **Content negotiation** | S-8, S-9 | Separate GET Accept headers from POST Content-Types; document `obsFormat` values |
| **Error handling** | S-4 | Gracefully handle 400/500 from unimplemented endpoints |
| **Infrastructure** | S-6, S-7 | Proxy/CORS guidance in library docs |
